# スーパー比較・買い物支援アプリ 壁打ちまとめ（2026-08-01）

## 概要
既存の要件整理（`Optimized tool selection.md`）を、実ユーザー（主婦層）へのヒアリング結果を踏まえて全体的に再検討した壁打ちの記録。ターゲット・トップ画面UI・ポジショニング・残タスクの4テーマを深掘りした。

## ヒアリングで得られた主な気づき
- 「曜日固定で店を決める」ルーティン型ユーザーがいる（例: 日曜はエブリイの冷凍食品）
- 価格より還元率が高い店を選ぶポイント重視派がいる
- ネットスーパー派・現地派でも判断軸が異なる
- 既存課題（誤タップ・カテゴリ誤判定・地図の説明不足）は裏付けが取れた
- 市役所サイトの「何を調べますか？」的な絞り込みUIが参考になりそう
- 既存の使いやすいサービスに例えられると覚えてもらいやすい（「あのスーパー版」）
- 「なぜ今これを作るのか（AI時代に）」のストーリーが言語化されていなかった

## 決定事項

### A. コア価値・ターゲット
- **コア価値**: 「行ったのに損したをなくす」から「自分の基準（価格/還元率/曜日）で最適解を提示する」に拡張
- **ターゲット**: 1つに絞らず、ルーティン型・ポイント重視派・ネットスーパー派・現地派を共通コア価値の上に並列展開する方針
- 優先順位づけの軸は「共通のコア価値を先に決める」を採用（機能はその上に個別に乗せる）

### B. トップ画面UI設計
- **第一接点は地図ファースト**（現在地の周辺店舗一覧から入る。「地図は初期設定として必須」）
- 既存課題（ピンの意味が分からない・説明がない）への対応:
  - 初回チュートリアルで一度説明
  - 地図画面上部にヘッダーを常設し、「何を見ているか」を一目で分かるようにする
- **設計原則**: 「誰も説明しなくても主婦が見るだけで使い方が分かる」

### C. ポジショニング・Whyストーリー
- **ポジショニング**: 「価格.comのスーパー版」（比較系）
- **Whyストーリー軸**: 自分自身の実体験・困りごと（行ったのに損した経験）を原点に言語化する

### D. 残タスクの優先順位
- 値下げタブの情報設計・サービス名検討・店舗ヒアリングはいずれも今回は着手せず保留
- 次回以降に優先順位を再検討する

## E. ビジネス化・収益化アイデア（`ideas/tokuchika-business-monetization.md` より統合）

秘書の `ideas/` フォルダにある事業化構想。「最安値検索アプリ」ではなく「今日の買い物でいくら得するかを即わかる家計アプリ」に軸足を移す方向性で、A〜Cで決めたコア価値（自分の基準で最適解を提示する）とも整合する。

### 課題・背景
現状は機能は揃っているが「安い商品を検索する」体験にとどまり、継続利用の動機（節約額の実感・毎日開く理由）が弱い。

### 解決策・機能アイデア（優先順位順）
1. **節約額表示** — 「A店が最安、B店より312円安い」「今月の累計節約額」を最初に見せる
2. **定番買い物リストの前面化** — いつもの朝食/カレー/鍋などを検索より先にワンタップ比較で出す
3. **値下がり通知** — お気に入り商品の値下げをプッシュ/メールで通知
4. **底値履歴（底値カレンダー）** — 商品ごとの通常価格・最近の安値・過去最安を可視化
5. **買い回り最適化・移動コスト込み比較** — 複数店舗を回った場合の得失、車/徒歩/ネット注文での判断材料

### 収益モデル案
1. ネットスーパーへの送客（成果報酬）※最初に狙うべきモデル
2. 月額プレミアム（¥200〜500/月）— 無料は比較・リスト・範囲指定、有料は値下がり通知・底値履歴・複数リスト・家族共有・広告非表示・節約レポート
3. 地域スーパー向け管理画面（特売掲載・近隣ユーザー通知・クーポン配信、B2B）
4. 地域広告（スーパー・ドラッグストア・八百屋・精肉店・弁当店・宅配サービス）
5. 物価データ活用（データ蓄積後、地域物価レポートを自治体/メディア/小売向けに展開）

### 短期で試すべき施策
- LP/トップの見せ方を「価格比較できます」→「今日の買い物でいくら安くなるか分かります」に変更
- SNS投稿しやすい結果画面（「B店より312円お得」等の共有画像）
- ユーザーインタビュー（子育て世帯・一人暮らし・親の買い物を手伝う人・車移動者・ネットスーパー利用者）

### SaaS化に向けた機能検討（`projects/price-compare-app/saas-features.md` より）
事業化フェーズで検討する拡張機能一覧。個人開発段階では全機能不要、着手時に優先順位を絞る前提。
- アカウント・マルチユーザー対応（世帯・家族共有含む）
- データ基盤の自動化（価格自動取得バッチ、JANコードマッチング精度、異常検知、店舗追加フロー）
- 通知・エンゲージメント基盤（プッシュ/メール、レコメンド）
- 収益化・プラン管理（無料/有料差別化、決済、店舗向け掲載・広告プラン、API提供）
- 運用・管理機能（管理者ダッシュボード、利用状況分析、サポート導線、法務対応）
- 継続検討事項: ネットスーパーごとの利用規約確認体制、価格データの著作権・利用許諾整理

## F. ワンタイムパスコード管理画面 設計（`2026-08-01-passcode-admin-panel-design.md` より統合）

2026-08-01に実装済みの機能設計。app.htmlのゲート用パスコードをコードのハードコードから脱却し、Zが手軽に確認・変更できるようにする最小スコープの管理画面。

### 背景・スコープ
- 従来 `src/lib/passcode.js` の `PASSCODE` 定数はハードコードで、変更にコード編集・ビルド・デプロイが必要だった
- 今回実装したのは「現在のパスコード表示＋新しい値への変更」のみ（ランダム生成・変更履歴・複数コード管理は対象外）
- 管理画面はLXC114（本番サーバー）にデプロイしつつ、nginxで `127.0.0.1` からのアクセスのみ許可（SSHポートフォワード経由でZがアクセス）

### 主な設計判断
1. **パスコード保存先をSupabase DB化**: 新規テーブル `app_settings`（単一行）。`anon` は SELECT のみ許可、管理画面からの更新は service role key でRLSをバイパス
2. **`checkPasscode` に `.normalize("NFKC")` を追加**: 全角文字入力（IME変換ミス）にも対応。既存レビューのMinor指摘の解消も兼ねる
3. **管理画面（admin.html）は別エントリーポイント**: `src/main-admin.jsx` → `src/pages/AdminPasscode.jsx`。service role keyを埋め込んだ `supabaseAdminClient.js` は `AdminPasscode.jsx` からのみimportし、公開バンドルへの混入を防ぐ
4. **nginxでadmin.html・関連アセットをlocalhost限定に**: Viteのマルチページビルドで `admin` 関連ファイルを `assets/admin/` ディレクトリ配下に明示的に固定し、nginx側もディレクトリ単位（`location ^~ /assets/admin/`）でブロックする方式に変更（当初案のファイル名パターンブロックは、将来的な参照変更で漏れうるという最終レビュー指摘を受けて修正）

### 既知の限界（最終レビューで記録済み）
- **パスコード自体は機密情報ではない**: `app_settings.passcode` はanonキーでSELECT可能なため、公開バンドルのanonキーを使えば誰でも直接取得できる。「厳密なアクセス制御」ではなく「URLを知らない人が迷い込むのを防ぐ簡易な導線」という位置づけ
- **`allow 127.0.0.1` が唯一の防御線・単一障害点**: LXC114に将来別のリバースプロキシ/トンネルを同居させると `$remote_addr` が127.0.0.1に化ける可能性があり、この防御が無効化されるリスクがある。追加する際は必ずこのnginx設定が機能しているか再検証する必要がある（秘書メモ: [[feedback_nginx_allow_cidr_tunnel_pitfall]] にも同種の教訓あり）
